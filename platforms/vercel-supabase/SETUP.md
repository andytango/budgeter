# Vercel + Supabase setup (agent runbook)

Deploys the app generated by `node tools/create.mjs vercel-supabase <APP>`: static files and Vercel
Functions on Vercel, data and sign-in (emailed one-time code) on Supabase. Free plans are enough, and no
custom domain is needed. Steps marked **USER** need the human; do everything else yourself.
Placeholders: `<APP>` generated folder, `<BUDGETER>` this repo, `<EMAIL>` the allowed address(es),
`<REF>` the Supabase project ref, `<HOST>` the app's hostname (e.g. `budgeter-abc.vercel.app`).

API shapes below were current when written. If a call is rejected, check the Supabase Management API
or Vercel CLI reference and adapt rather than guessing.

## 0. Prerequisites

**USER** provides two tokens as environment variables (in Claude Code on the web: the environment's
settings, not the chat). On a local machine, `npx supabase login` / `npx vercel login` work instead.
- `SUPABASE_ACCESS_TOKEN`: supabase.com → Account → Access Tokens → Generate new token.
- `VERCEL_TOKEN`: vercel.com → Account Settings → Tokens → Create.

`$MGMT` below = `https://api.supabase.com/v1`, always with `-H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN"`.
To run SQL: `POST $MGMT/projects/<REF>/database/query` with `{"query": "<sql>"}`; build the body from
the file with `jq -Rs '{query: .}' file.sql`.

## 1. Supabase project

- Existing project: ask for its ref (the `<REF>` in `https://<REF>.supabase.co`).
- New project: `GET $MGMT/organizations` → the organization's `slug`; then
  `POST $MGMT/projects` with `{"name": "budgeter", "organization_slug": "<slug>", "db_pass": "<random 32+ chars>",
  "region_selection": {"type": "smartGroup", "code": "emea"}}` (`americas` / `emea` / `apac`: nearest
  the user). Poll `GET $MGMT/projects/<REF>` until `status` is `ACTIVE_HEALTHY` (a few minutes).
  You don't need to keep the database password.

## 2. Tables

Run `<APP>/schema.sql` via the query endpoint. Check:
`select relname, relrowsecurity from pg_class where relname in ('docs','push_subs','notifications')`
→ three rows, all `true`.

## 3. Keys

`GET $MGMT/projects/<REF>/api-keys?reveal=true` → the `publishable` key (`sb_publishable_…`) and a
`secret` key (`sb_secret_…`). If there are none of those types, create them:
`POST $MGMT/projects/<REF>/api-keys` with `{"type": "publishable", "name": "default"}`, and
`POST $MGMT/projects/<REF>/api-keys?reveal=true` with
`{"type": "secret", "name": "default", "secret_jwt_template": {"role": "service_role"}}`.
(Legacy `anon` / `service_role` keys also work, as publishable / secret.)
`SUPABASE_URL` = `https://<REF>.supabase.co`. The secret key is a secret: store it, never print it.

## 4. Sign-in

1. Emails send a code, not a link (a link would open Safari instead of the Home Screen app), and
   sign-ups are off: `PATCH $MGMT/projects/<REF>/config/auth` with
   ```json
   {"disable_signup": true,
    "mailer_subjects_magic_link": "Your Budgeter code",
    "mailer_templates_magic_link_content": "<h2>Your Budgeter code</h2><p>Enter this code in the app: <strong>{{ .Token }}</strong></p>"}
   ```
2. Create each allowed user (works with sign-ups off):
   `POST https://<REF>.supabase.co/auth/v1/admin/users` with headers `apikey: <secret key>` (plus
   `Authorization: Bearer <key>` if it's a legacy JWT key) and `{"email": "<EMAIL>", "email_confirm": true}`.
3. Supabase's built-in email only delivers to members of the Supabase organisation, with a low hourly
   limit. The account owner's own address is fine. For anyone else, **USER** either invites them to
   the organisation or sets up custom SMTP (dashboard → Authentication → Emails → SMTP Settings).

## 5. Push keys and cron secret

```sh
node <BUDGETER>/tools/gen-vapid.mjs > /tmp/vapid.json      # outside any repo; delete after step 6
openssl rand -hex 32 > /tmp/cron-secret                    # CRON_SECRET; also delete after step 7
```

## 6. Vercel

From `<APP>` (add `--token "$VERCEL_TOKEN"` to every command when using a token):
```sh
npx vercel link --yes --project budgeter
npx vercel env add SUPABASE_URL production --value "https://<REF>.supabase.co" --yes
npx vercel env add SUPABASE_PUBLISHABLE_KEY production --value "<publishable key>" --yes
npx vercel env add SUPABASE_SECRET_KEY production --value "<secret key>" --sensitive --yes
npx vercel env add ALLOWED_EMAILS production --value "<EMAIL>" --yes          # comma-separated
npx vercel env add VAPID_PUBLIC_KEY production --value "<publicKey>" --yes
npx vercel env add VAPID_PRIVATE_JWK production --value '<privateJwk>' --sensitive --yes
npx vercel env add VAPID_SUBJECT production --value "mailto:<EMAIL>" --yes
npx vercel env add CRON_SECRET production --value "$(cat /tmp/cron-secret)" --sensitive --yes
npx vercel deploy --prod --yes
```
Use `--value`: piping the value on stdin has stored empty values in some CLI versions. Check with
`npx vercel env ls production` (8 variables). `<HOST>` is the production URL the deploy prints (or
`npx vercel project inspect budgeter`). Optional: **USER** adds a custom domain in the Vercel
dashboard, and/or connects the private repo (Root Directory = the app folder) so pushes deploy.
Vercel protects preview deployments by default; production is public, which is fine because the
data needs sign-in.

## 7. Every-minute delivery

Fill in `<APP>/cron.sql` (`REPLACE_ME_APP_HOST` = `<HOST>`, `REPLACE_ME_CRON_SECRET` = the secret) in a
temp copy, run it via the query endpoint, and delete the copy and `/tmp/cron-secret`. Don't commit the
filled-in file. Two minutes later:
`select status_code, content from net._http_response order by id desc limit 3` → `200`, `{"sent":0}`.
(On Vercel Pro you can use Vercel Cron instead: add `"crons": [{"path": "/api/cron/deliver", "schedule": "* * * * *"}]`
to `vercel.json` and redeploy; Vercel sends the `CRON_SECRET` header itself. On Hobby, that fails the deploy.)

## 8. Load a budget

Load the demo first to check everything, then the user's real budget once it exists (AGENTS.md, phase 4):
```sh
node <BUDGETER>/tools/validate.mjs <budget.json>
node <BUDGETER>/tools/make-seed.mjs <budget.json> --postgres > /tmp/seed.sql
jq -Rs '{query: .}' /tmp/seed.sql | curl -s -X POST "$MGMT/projects/<REF>/database/query" \
  -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" -H "content-type: application/json" --data-binary @- && rm /tmp/seed.sql
```

## 9. Verify

- `curl -s -o /dev/null -w '%{http_code}\n' https://<HOST>/api/budget` → `401`. A 200 means the data
  is public: stop and fix.
- `curl -s https://<HOST>/api/config` → the Supabase URL and publishable key only.
- `curl -s -o /dev/null -w '%{http_code}\n' https://<HOST>/api/cron/deliver` → `403`.
- **USER**: open `https://<HOST>` on their phone, enter their email, type the emailed code, see the budget.
- Push, once the user has tapped the bell (AGENTS.md, phase 5): run
  `insert into notifications (title, body) values ('Budget', 'Test from setup')`, then a minute later
  `select sent_at, result from notifications order by id desc limit 1` → `result` like `201`.

## Day to day

- Code changes: `node <BUDGETER>/tools/create.mjs vercel-supabase <APP> --update`, then `npx vercel deploy --prod --yes`
  (or push, if the repo is connected).
- Data: written by the daily routine (see `snippets.md`); no deploy needed.
- Supabase pauses free projects after a week with no activity; the daily routine keeps it awake. If it
  does pause, **USER** restores it from the dashboard.
